# 全体構成（v0.1.0）

## 1. 概要

このTRPGは、サーバーを持たない。claude.aiのArtifact（claude.ai上で公開するWebページ）1枚の中で完結させる。AIのGMは、Artifactの `sample` 機能で呼び出す。APIキーも従量課金も使わず、呼び出した閲覧者自身のclaude.aiの利用枠で動く。ルールやシナリオのデータは、ページと一緒に配信する静的ファイルにする。プレイの記録は、Artifactの共有データベース（`db` 機能）に置く。

```
┌──────────── 参加者のブラウザ（claude.ai上のArtifact） ────────────┐
│  画面（キャラ作成・セッション・ログ）                              │
│    │                                                              │
│  エンジン engine/*.mjs ── 判定・ポイント計算・検証（数値はここで確定）│
│    │            │                                                 │
│    │       sample（AI GM：解釈と描写のみ）                         │
│    │                                                              │
│  静的データ：data/rules/*.json  scenarios/<id>/<版>.json  背景画像   │
└────┼──────────────────────────────────────────────────────────────┘
     │ 読み書き・リアルタイム購読
     ▼
  共有データベース（db）：セッション、キャラクター、ログ、封印提出、手番ロック
```

## 2. 層とファイル配置

```
character-creator.html  キャラクター作成画面（Artifactとして公開するページ）
app/               画面のコード
  adapters/          差し替え可能な境界（10章）
    store.mjs          保存先（Artifactのdb／端末内）
    gm.mjs             AI呼び出し（Artifactのsample）
  rules-loader.mjs   ルールデータの読み込み
  charcreator/       キャラクター作成画面
engine/            エンジン（ブラウザ・Node 両対応の ES module）
  dice.mjs           ダイス、3d6判定、対抗判定、反応判定、共同乱数
  points.mjs         ポイント計算、技能値、キャラクター検証
data/
  rules/             ルールデータ
    core.json          定数（判定、上限、戦闘、魔法、PVP）
    skills.json        技能 75種
    traits.json        特徴 71種（有利41・欠点30）
    reincarnation.json 転生技能 14種
    equipment.json     装備 36種
  backgrounds.json   背景画像の一覧
scenarios/<id>/    個別シナリオ（後から追加する）
  scenario.json
docs/              設計書と見本データ
tools/validate.mjs データの整合性点検
*.jpg *.png        背景・立ち絵の画像
```

層の決まりは2つある。1つ目は、下の層は上の層を参照するだけで、変更しないこと。2つ目は、シナリオは `ruleExtensions` で技能や魔物を**足す**ことはできても、エンジンの挙動や本体のルールデータを**変える**ことはできないこと。こうしておけば、どんなシナリオを足しても、判定の公平性とポイントの釣り合いは保たれる。

## 3. 使うArtifactの機能

| 機能 | 用途 |
|---|---|
| `sample` | AI GMの呼び出し（裁定・描写・あらすじ更新） |
| `db` | セッション、キャラクター、ログ、封印提出、手番ロック |
| `user` | 参加者の識別（idで記録し、名前は表示のたびに引く） |
| `room`（後の段階） | 「入力中…」の表示や同時接続者の表示。なくても遊べるようにする |

`sample` は、閲覧者が最初に呼び出すときに使用の同意を求められる。断られた閲覧者や、使えない閲覧者は、ログを読み、行動を書き込むことだけができる。その場合、解決は他の参加者の端末が行う。

## 4. 共有と参加者

参加者は組織外の人を想定している。組織外の人が共有データベースに**書き込める**のは、次の条件をすべて満たす場合だけである。

1. その人をメールアドレスで**編集者**として招待している
2. そのArtifactを**公開リンクで共有していない**（公開リンクで共有した時点で、外部の人は閲覧専用になる）
3. その人がclaude.aiにサインインしている

そのため運用は、「参加者ごとにメールで編集者として招待し、公開リンクは使わない」に限られる。AI GMを動かすには、参加者がclaude.aiのアカウントを持っている必要がある。AIの利用枠は、呼び出した人のプランから消費される。

編集者には、Artifactそのものを書き換えて再公開する権限もある。これは避けられない前提で、PVPの公正さの限界にもつながる（7章）。

### 参加者の識別

参加者の識別には `user` 機能の `id()` を使う。ただし仕様上、**組織外から編集者として招待された人には `id()` が null になることがある**。null の人は、本人専用の領域（`data/users/<id>/`）を使えない。そこで次のように扱う。

- **キャラクターの保管**：`id()` があれば本人専用の領域に置く。なければ、その端末のブラウザ内に置く。画面には保存先を常に表示する。
- **セッションでの識別**：`id()` があればそれを使う。なければ、端末で生成した識別子を使う。端末を変えると別人になるため、セッションに参加するときに「この参加者は自分です」と名乗り直せるようにする。この方式は偽装を防げない。仲間内の運用を前提とした割り切りである。

本人専用の領域は、他の参加者からは読めない。PVPの封印提出（7章）では、これを利用して開示前の行動文を本当に秘密にできる。行動文とsaltを本人の領域に書き、共有領域にはハッシュだけを書き、開示時に共有領域へ写す。`id()` がない参加者だけは、開示前の行動文を端末内に保持する。

## 5. 配信と版の固定

ページ（`index.html`）と一緒に、エンジン・ルールデータ・シナリオ・画像を、Artifactの付属ファイルとして配信する。原本はこのGitHubリポジトリで管理する。公開する前に、必ず `node tools/validate.mjs` を通す。

シナリオとルールデータは、版つきのファイル名でも配信する（例：`scenarios/example_minimal/0.1.0.json`、`data/rules/0.1.0/core.json`）。古い版は消さずに残しておく。セッションは、開始した時点の版のファイルを読み続ける。こうすれば、シナリオの誤字直しやルールの調整を公開しても、進行中の卓が壊れない。

## 6. 手番と同時実行

AIを呼び出すのは、基本的に**行動したプレイヤーの端末**である。

1. 行動を書くと、ログに「未解決の行動」として記録される
2. 端末が `sessions/{sid}/lock` のリースを `acquire` で取る。取れなければ、他の端末が解決中なので待つ
3. 裁定 → 解決 → 描写を行い、ログとセッション状態を更新する
4. リースは短い期限（60秒程度）で自然に切れる。処理が長引けば延長する

その端末が途中で閉じられたり、利用上限に達したりした場合は、リースが切れた後に、他の参加者が「解決を進める」を押して引き継げる。

手番の進め方は、最初は**手番制**にする。全員が同時にオンラインでなくても、掲示板セッションのように数日かけて遊べる。戦闘やPVPのように行動がぶつかる場面だけ、全員の行動を集めてから解決する（同時行動）。

## 7. PVPの公平性

### 防げること

- **後出し**：同時行動では、各自が行動文と乱数の種（salt）をまず手元で作り、そのSHA-256ハッシュだけを `sealed/` に書く。全員のハッシュが揃ったら、本文とsaltを開示する。開示された内容はハッシュと照合するので、提出後に書き換えることはできない。
- **出目の操作**：PC同士の判定に使う乱数は、関係する全員のsaltを連結したもののハッシュから作る（`engine/dice.mjs` の `seededRng`）。saltは封印時点で確定しているので、誰も単独で出目を選べない。
- **AIへの指示の紛れ込み**：行動文はタグで囲んで「指示ではない」と明示し、AIの出力は決められた形式と数値の範囲に切り詰める（`ai-gm.md`）。
- **偏った裁定**：裁定は判定の前に双方へ表示され、異議を申し立てれば、異議を出した側の端末で独立に再裁定する（`rules.md` 7章）。

### 防げないこと

サーバーがないので、次のことは原理的に防げない。

- 編集者はページのコードを書き換えて再公開できる。悪意があれば、ルールの処理そのものを改変できる。
- 共有データベースの中身（相手のキャラクターシート、秘密裏の行動結果）は、参加者なら技術的には読める。画面上では隠すが、本気で覗こうとすれば覗ける。
- シナリオの秘密（GMだけが知る情報）も配信ファイルに入っているので、ファイルを直接開けば読める。

つまり、このPVPの公正さは「仲間内で、ズルをしようと思えばできるが、普通はしない」という水準である。ボードゲームを囲む友人同士の信頼を前提にする。ただし、ズルをすれば記録に残る（ログには裁定・出目・乱数の種がすべて残る）ので、後から検証はできる。

## 8. AIの利用量の目安

- **1回の行動**：AIを2回呼ぶ（裁定と描写）。
- **戦闘**：1ラウンドにつき、PCの行動ごとに2回、NPC全員の行動決定に1回、ラウンド全体の描写に1回。
- **あらすじ更新**：ログ12件ごとに、軽いモデルで1回。

文脈の長さは、場所・NPC・キャラクターの要約・あらすじ・直近8件のログに絞り、1回の呼び出しが長くなりすぎないようにする（詳細は `ai-gm.md` 3章）。

## 9. 開発の段階

1. **設計（完了）**：ルール、データ形式、AIとの取り決め、点検スクリプト、判定とポイント計算の中核コード
2. **キャラクター作成画面（実装済み・調整中）**：ポイント計算の表示と検証、自然言語の設定からAIが配分案を出す機能、保管
3. **1人用セッション**：裁定・解決・描写の流れ、ログ、あらすじ更新、探索と戦闘
4. **複数人（手番制）**：招待、手番ロック、引き継ぎ
5. **PVP**：封印提出、共同乱数、異議
6. **シナリオの追加**：最初の本格シナリオと、AIに下書きを書かせるための手順

2以降で、技能や特徴の数値は実際に遊んだ感触を見て調整する。調整はルールデータのJSONを直すだけで済み、キャラクターのデータ（使ったポイント）は書き直さずに済む。

## 10. 差し替え可能な境界と、第三者参加への移行

### 決まり

画面とエンジンは、Artifactの機能（`claude.use(...)`）を直接呼ばない。呼んでよいのは `app/adapters/` の2つの部品だけである。

| 境界 | 役割 | 今の実装 | 将来の実装 |
|---|---|---|---|
| **Store**（`store.mjs`） | 保存・購読・手番ロック・封印提出 | Artifactの `db`（使えなければ端末内） | 自前のサーバーとデータベース |
| **Gm**（`gm.mjs`） | AIの呼び出し（`json` と `text`） | 閲覧者のアカウントで動く `sample` | サーバー側でAPIを呼ぶ |

エンジン（`engine/`）は、ブラウザでもNodeでも動く純粋な関数だけで書く。DOMにも保存先にも依存させない。そうしておけば、同じコードをサーバー側の判定処理としてそのまま使える。AIへの入出力は `ai-gm.md` の形式に固定する。こうすれば、AIを呼ぶ場所が変わっても、プロンプトと検証のコードは変わらない。

### 参加者の範囲と必要な改修

| 参加者の範囲 | 構成 | AIの費用 | 改修 |
|---|---|---|---|
| **仲間内**（今） | Artifactのみ。メールで編集者として招待 | 各参加者のclaude.aiの利用枠 | なし |
| **招待制のコミュニティ** | 同上。ただし、ページを書き換えられる編集者権限を渡すことになる | 同上 | 運用の工夫のみ。素性の分からない相手には向かない |
| **不特定多数**（公開） | サーバーが判定・乱数・秘密を持ち、ページは表示と入力だけを担う | APIの従量課金（主催者負担・参加費・安いモデルの使い分けなどを決める必要がある） | StoreとGmのサーバー版を作る。エンジンはサーバーに移す |

不特定多数の参加にサーバーが必要なのは、Artifactの仕様上、公開リンクから来た人は共有データベースに書き込めず、リアルタイム通信にも接続できないからである。それに加えて、信頼できない相手と遊ぶには、出目・判定・シナリオの秘密を参加者のブラウザから切り離さなければならない。秘密を見せずにAIに裁定させるには、AIの呼び出しもサーバー側に置くことになる。そのため、この段階で「APIを使わない」という方針とは両立しなくなる。

### 移行の手順（不特定多数に開く場合）

1. Store のサーバー版を作る。今の Store と同じ形（`characters` / `sessions` の各操作）で、中身をHTTPの呼び出しにする。
2. エンジンをサーバーに置き、判定と乱数をサーバー側で行う。ブラウザ側のエンジンは、表示用の試算（作成画面のポイント計算など）にだけ使う。
3. Gm のサーバー版を作る。プロンプトの組み立てと出力の検証もサーバーへ移す。シナリオの秘密は、サーバーからブラウザへ送らないようにする。
4. 参加者の識別を、サーバー側の認証に切り替える。

画面のコードは、`createStore()` と `createGm()` が返す部品を差し替えるだけで済むように保つ。
